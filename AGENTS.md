# Loomis — правила работы агентов

## 1. Маршрутизация задач по моделям

### flash — базовая роль (deepseek-v4.1-flash)
Основной рабочий профиль. Использовать по умолчанию для:
- каркаса проекта и структуры папок;
- БД PostgreSQL/SQLite на SQLAlchemy (модели, миграции, запросы);
- Telegram-бота на Aiogram 3;
- парсинга PDF, DOCX и ГС;
- вёрстки UI;
- обычных CRUD-операций и мелких правок.

### core — сложная логика (gpt-6.2-sol)
Использовать для:
- ядра оркестратора;
- WebSockets и realtime-взаимодействия;
- таймеров и фоновых задач;
- Git-моста;
- адаптеров внешних API;
- сложной интеграции компонентов.

Правило делегирования: если ты запущен в профиле `flash` или `cheap` и видишь
задачу из списка выше — НЕ бери её сам. Делегируй:

```
codex exec --profile core "ТЗ: <что сделать>. Файлы: <пути>. Не трогай остальное."
```

После возврата проверь diff/выход и продолжай в текущем профиле.

### cheap — дешёвые задачи (gpt-6-luna)
Использовать для:
- тестов pytest;
- README и документации;
- конфигов и служебных файлов;
- мелких правок и переименований.

Вызов:

```
codex exec --profile cheap "<задача>"
```

### heavy — только по разрешению (claude-sonnet-5-5)
ЗАПРЕЩЕНО вызывать профиль `heavy` без явного ручного разрешения пользователя.
Бюджет проекта — $5. Перед любым обращением к `heavy` спроси пользователя
и дождись ответа. Для рутины `heavy` не использовать никогда.

## 2. Контроль бюджета

- Цель: уложиться в $5.
- Начинать с `flash`; `core` — только для сложных задач; `cheap` — для
  тестов, документации и конфигов.
- Не перечитывать большие файлы повторно без необходимости.
- Не запускать дорогие модели «на всякий случай».
- При сомнении между `core` и `heavy` — всегда `core`.

## 3. Память проекта

Перед началом работы прочитать `SPEC.md` и `STATE.md` (если файла нет —
пропустить и отметить это в `STATE.md`).

После каждой выполненной подзадачи:
1. Обновить `STATE.md`: что сделано, что осталось, следующий шаг.
2. Вывести в конце ответа строку:

```
 ЗАДАЧА ВЫПОЛНЕНА. Начни новую сессию для сброса контекста и экономии баланса.
```

## 4. Границы изменений

- Не менять файлы вне выданного ТЗ.
- Не делать `git commit` и не создавать ветки без просьбы пользователя.
- Соблюдать стиль существующего кода; изменения — минимальные и по делу.
